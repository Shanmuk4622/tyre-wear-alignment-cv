# 16 — Hugging Face Repository Structure

> HF is **the only permanent store**. Kaggle sessions are disposable; `/kaggle/temp` is wiped; `/kaggle/working` is 20 GB. If it is not on HF, it does not exist.
>
> Decide this layout **before the first run**. Restructuring after 800 runs means rewriting every analysis path.

---

## 1. Repositories

| Repo | Type | Visibility | Contents |
|---|---|---|---|
| `Shanmuk4622/tyre-wear-study` | **dataset** | **public since 2026-08-27** | **Everything.** Runs, metrics, XAI, annotations, tables, paper |
| `Shanmuk4622/tyre-wear-models` | model | private | Optional — only the 3–5 final release checkpoints with model cards |

### Why one repo for the study

**The write limit is per user, not per repo.** Two active repos means two commits per push cycle for no benefit, and it halves your effective budget.

### Why a *dataset* repo rather than a model repo

HF renders **CSV and Parquet previews in the browser** for dataset repos. Every metrics table becomes browsable without downloading anything — which matters enormously when you want to glance at 800 runs from a phone. Model repos do not do this.

Checkpoints live in the dataset repo too. That is unconventional and correct here.

## 3. Run ID scheme

Deterministic and readable. **Never a UUID** — in six weeks you need to find a run by reading its name.

```
{stage}-{arch}-{technique}-f{fold}-s{seed}
```

| Example | Meaning |
|---|---|
| `a-convnextv2_t-base-f0-s1` | Stage A, ConvNeXt-V2-T, standard recipe, fold 0, seed 1 |
| `b-convnextv2_t-roi_tyre-f1-s3` | Stage B, mask-derived tyre ROI factor |
| `b-effnetv2s-res512-f1-s2` | Stage B, 512-pixel resolution factor |
| `d-yolo26n-det_manual-f0-s1` | Stage D, YOLO26-n on manual boxes |
| `t8-pipeline_full-f0-s1` | Tier 8, the integrated pipeline |

Rules: lowercase, no dots, no spaces. Hyphens delimit the five fields;
underscores are allowed inside architecture and technique names. `technique`
is `base` in Stage A. Sortable by stage, then architecture.

## 4. Push tiers and cadence

Not everything deserves the same frequency.

| Tier | Contents | Cadence | Size |
|---|---|---|---|
| **light** | `config.yaml`, `STATUS.json`, `metrics/*.csv`, registry event | every 30 min | KB |
| **heavy** | `checkpoints/ckpt_last.pt` | every 30 min | 100–350 MB |
| **bulk** | `telemetry/*`, `xai/saliency/*`, `per_sample/*.parquet` | every 10 epochs + at end | MB–GB |
| **flush** | everything pending | on interrupt / SIGTERM / atexit | — |

**Batch into one commit.** `create_commit` with many `CommitOperationAdd`s is **one** rate-limit operation, not N. This is the single biggest saver.

In tyrelib v6 (retaining the v5 policy) an ordinary static-owner `claimed` event is light data and rides
this batch. Only an explicitly stolen claim flushes immediately. The old
per-claim flush exhausted a worker's 25/hour cap while training sat idle.

### Budget — settled

**One HuggingFace account: `Shanmuk4622`. Token in Kaggle Secrets as `HF_TOKEN`.**

All four Kaggle accounts push with that one token, so the whole team draws from **one shared budget**:

```
HF limit ≈ 128 write ops / hour / USER
cap per worker = 100 / NUM_WORKERS      (tyrelib sets this automatically)
```

| NUM_WORKERS | Cap each | Team total |
|---:|---:|---:|
| 1 | 100/hr | 100/hr |
| 2 | 50/hr | 100/hr |
| **4** | **25/hr** | **100/hr** |

28 ops/hour of headroom under the 128 ceiling.

At a 30-minute cycle a 9-hour session emits ~18 scheduled commits, plus a handful of event-driven ones. Comfortably inside — but the headroom is what absorbs four workers finishing models at the same moment.

**Nothing to decide.** `tyrelib.Session` computes the cap from `NUM_WORKERS`; the limiter is keyed by token hash and is process-wide, so it cannot be accidentally multiplied by having several uploader objects.

### When a commit actually happens

| Trigger | Blocking? |
|---|---|
| Background cycle, every 30 min | no |
| End of every epoch — metrics + checkpoint enqueued | no (rides the cycle) |
| Every 10 epochs — telemetry, per-sample predictions | no |
| Ordinary static-owner claim | no (rides the cycle) |
| Explicitly stolen claim | yes — immediate coordination boundary |
| **A model finishes** | **yes — immediate blocking flush** |
| **A model pauses cleanly** | **yes, then the worker stops** |
| **End of an important cell** (`sess.push_now()`) | **yes** |
| **You press Stop / SIGTERM / an exception** | **yes — emergency flush** |
| 8.5-hour watchdog fires | yes, then pause cleanly |
| `sess.finish()` | yes, then verify by re-listing |

## 5. Checkpoint storage — the one thing that will bite you

~800 runs × ~200 MB = **~160 GB** if you keep every checkpoint. That is a lot of LFS.

### Retention policy

| Keep | Which runs |
|---|---|
| `ckpt_best.pt` **and** `ckpt_last.pt` | Top 5 architectures, all folds and seeds |
| `ckpt_best.pt` only | Everything else in Stage A |
| Both checkpoints while the study is active | Stage B OFAT runs; keep the only training copy on HF |
| Everything | Tier 8 integrated pipeline |

**Rationale:** XAI needs weights, so any model entering Stage E must keep
`ckpt_best`. The project rule is also “train once”, so Stage-B checkpoints stay
on HF while the study is active. Kaggle scratch copies are deleted only after
both checkpoint paths are re-listed publicly. A later archive pass may retain
only `ckpt_best` after the final analyses are frozen.

Storage will grow during NB06 because resumability takes priority over early
deletion. Monitor HF storage and apply the `ckpt_best`-only archive pass only
after NB10 has frozen every result that may need a checkpoint.

Delete only via **confirm-then-delete**:

```python
ok = sync.flush(timeout=1800)
missing = sync.verify_present([f"runs/{run_id}/checkpoints/ckpt_best.pt", ...])
if ok and not missing:
    shutil.rmtree(run_dir)      # only now
```

A flush that merely did not time out is **not** evidence the files arrived. Re-list the repo.

## 6. The registry — the part that silently breaks

### ⚠ HF has no append operation

Every worker appending to a shared `runs.jsonl` and pushing means **the last push silently destroys every other worker's lines.** No error. The file just forgets. Two runs training, ledger lists one.

**This is expensive, not cosmetic:** work planning reads *completion* from the ledger, so a lost `completed` entry makes a finished 3-hour run look unfinished, and someone retrains it.

### Fix: one shard file per writer

```
registry/events/{account}_w{worker}_{session}.jsonl
```

Nobody else ever touches your shard. Reads merge every shard, sort by float timestamp, and apply sticky terminal states.

```python
def latest(self):
    st = {}
    for e in self.entries():                    # merged from all shards
        rid = e["run_id"]
        if st.get(rid, {}).get("state") == "completed" and e["state"] != "completed":
            continue                            # sticky — don't resurrect
        st[rid] = e
    return st
```

**Store float epoch timestamps.** ISO strings at second granularity sort ambiguously across shards — exactly where ordering must be trustworthy.

### Event schema

```json
{"ts": 1787654321.123, "iso": "2026-08-27T09:12:01Z",
 "run_id": "a-convnextv2t-base-f0-s1", "state": "running",
 "account": "acctA", "worker": 0, "session": "s7f3a2",
 "epoch": 12, "best_qwk": 0.71, "wall_s": 1840.2,
 "host": "kaggle", "lib_version": "v3"}
```

States: `claimed` → `running` → (`paused` | `completed` | `failed`).

## 7. Aggregation

### ⚠ `tables/all_runs.csv` is a trap — use `all_runs_remote.csv`

`Session.aggregate()` globs the **local staging directory**. On a four-account
run each account therefore writes a table of the eleven runs it happened to do,
and each overwrites the last. After Stage A, `tables/all_runs.csv` held 11 rows
out of 36 and looked completely normal.

Use `Session.aggregate_remote()`, which lists the repository, downloads every
`runs/*/metrics/final.csv`, and writes `tables/all_runs_remote.csv`. It also
warns when a `run_id` appears twice — which is how the duplicate-training bug
(`05 §7`, Bug 13) becomes visible instead of silently averaging two identical
rows.

```
registry/ + runs/*/metrics/  ──▶  tables/all_runs_remote.csv   ← every account
                             ──▶  tables/all_epochs.csv
                             ──▶  tables/xai_summary.csv
```

**`tables/` is generated, never hand-edited.** Everything in the paper derives from it, so a stale table means a wrong paper.

### Current public XAI gate — verified 2026-08-30

NB07 revision `2026-08-30-r3` is complete in the public dataset. The live
files contain 1,208 rows in `xai_evidence_all.csv`, 35 rows in
`xai_faithfulness.csv`, and 18 rows in `stage_b_selection.csv`. The locked
Stage-B set is `regnety016`, `densenet121`, and `resnet50`; each has
`xai_status=ok` and seeds 1–3. Raw valid TER coverage is 180/180, 178/180, and
180/180 respectively. NB06 re-derives this coverage from the raw evidence
before it starts training.

### Current public Stage-B execution — verified 2026-09-03

There are **76 `runs/b-*` status files: 42 completed and 34 checkpointed
incomplete**, with 32 of the planned 108 runs not yet started. All 76 have both
`checkpoints/ckpt_last.pt` and `ckpt_best.pt`; the at-risk count is zero.

Tyrelib v11 keeps the same registered models/configs and the repaired
contiguous RegNet CUDA path. It serialises one complete state per epoch,
snapshots that file to `ckpt_best` on improvement, trims freed Linux
checkpoint/upload arenas, and batches normal pushes into the 30-minute commit.
Each NB06 model runs in a disposable child process, so the operating system
reclaims native/PyTorch/CUDA state that survived in-process cleanup. A
RAM-paused child publishes its epoch and the parent resumes the same run in a
clean child. A fresh Kaggle session can likewise fetch every public rolling
checkpoint and continue.

Two 60-row histories combined a 177-column v4 header with 178-value v5 rows.
The checkpoints were valid; only pandas parsing failed. v6 migrates this known
revision insertion losslessly, writes one canonical header atomically, and
performs all future epoch updates by column name rather than positional append.

### What a run directory actually contains

Verified against the live repository after Stage A — 12 files per run:

```
runs/<run_id>/
├── STATUS.json                     ← the completion source of truth
├── summary.json                    ← added after Bug 14; was missing for all of Stage A
├── split_health.json               ← tyre count per fold + leak flags
├── config.yaml
├── env/environment.json
├── metrics/{epochs.csv, final.csv, confusion_matrix.csv}
├── per_sample/predictions.parquet
├── checkpoints/{ckpt_last.pt, ckpt_best.pt}
└── telemetry/{energy_samples.csv.gz, system_samples.csv.gz, step_traces.jsonl}
```

**Completion is `STATUS.json.status == "completed"`, nothing else.** Judging it
by the presence of a file gave 36 false negatives when that file turned out
never to be uploaded. One definition, in one place: `RemoteInventory.state()`.

The aggregator also **audits**:

- Every expected run present? Which are missing?
- Any run marked `completed` with a truncated `epochs.csv`? → **broken stub**, demote to `paused` or it is skipped forever
- Any run with `nan_or_inf_batches > 0`?
- Any run whose `config_hash` disagrees with its `config.yaml`?

Write the audit to `tables/audit_report.json` and read it at the Friday meeting.
